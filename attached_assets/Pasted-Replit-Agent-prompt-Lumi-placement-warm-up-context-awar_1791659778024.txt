You are working inside the existing Lumi project. Lumi is a responsive website with an AI tutor for kids (6 to 12) with dyslexia, learning difficulties or autism. Adults (teachers or parents) create child accounts and assign the condition. Children log in with username + PIN and chat with Lumi in a mode built for their condition. One backend, one chat API, three mode frontends.

Do not rebuild or restyle what already exists. Use the project's existing stack, database, auth, routing, design tokens and TTS. Add only what this prompt describes.

What we are building
A placement warm-up ("يلا نتعرّف!") the child does the first time they log in, one per condition.
Deterministic scoring that turns answers into levels, a band, flags, interests and preferences.
A learner context built from that result and injected into the tutor's system prompt on every chat call, so Lumi adapts from the first message.
A "Starting point" card on the adult's student profile, plus seeded profile insights.
Non-negotiable rules
The warm-up is never called a test or exam in the child UI.
No AI in scoring. Scoring is pure code from the rules in the MD files.
The child never sees scores, levels, flags, right/wrong, or red. Same neutral reaction after every answer (defined per file).
The AI never diagnoses, never names the condition to the child, never mentions levels or the warm-up results to the child.
A child only ever sees their own mode's routes. The warm-up lives inside each mode's frontend (e.g. /dyslexia/warmup, /ld/warmup, /autism/warmup). Match the existing route naming.
Mode UI rules apply during the warm-up (dyslexia: auto audio, big text; learning difficulties: one item per screen + Next; autism: visual schedule, no animations, fixed layout).

Phase 3: Scoring

Write one pure function per test: scorePlacement(test, answers) → result, implementing section 4 of each MD file exactly (points per item, level thresholds, band, step size for learning difficulties, flags, error patterns for dyslexia, signals). Output must match section 5 of each file.

Write unit tests with at least 3 fixtures per test (low, mixed, high). The mixed fixtures must trigger the hidden-strength flags: understands_more_than_reads, reasons_beyond_school_level, academically_ready.

When a placement finishes: run scoring, save result, set status = done, then seed insights (Phase 5).

Phase 4: Learner context + chat
buildLearnerContext(result) → string. Deterministic, no AI. Uses the context block template in section 7 of the matching MD file and includes one line per applicable tutor rule from section 6.
In the existing chat API, assemble the system prompt in this order:
   [BASE RULES]      shared safety rules (below)
   [MODE PROMPT]     the existing system prompt for the child's mode (do not change it)
   [LEARNER CONTEXT] buildLearnerContext(active placement result)
   [RECENT INSIGHTS] up to 5 latest profile_insights for this student (both sources), as bullet lines

then the chat history. 3. BASE RULES text:

   You are Lumi, a kind learning helper for a child aged 6 to 12.
   - You help the child learn. You never diagnose and never name any condition.
   - Never tell the child about levels, scores, flags, tests or what their teacher or parent sees.
   - Never call the child smart, weak, slow or any label. Praise effort and thinking.
   - Follow LEARNER CONTEXT strictly. It tells you the child's starting level, step size, text limits and interests.
   - Start at the band's level. After 3 correct in a row, make it a bit harder. After 2 wrong in a row, make it easier and give an example.
   - Use the child's interests in examples.
   - If the child seems upset or says something worrying about their safety, respond gently and tell them to talk to their teacher or parent.
If a student has no active placement (old accounts), the chat still works without the LEARNER CONTEXT block.
Cache the context string on the placement row if needed, but rebuild it whenever the result changes.
